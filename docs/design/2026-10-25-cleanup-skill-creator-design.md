# 清理 Skill Creator 与聊天任务面板设计草案

日期：2026-10-25。状态：待讨论，尚未进入实现。本文件是中立设计草案，未确认、归档或改变现有 Comet 需求。

## 目标与决定

通过聊天、用户文档和网址创建可复用的清理 Skill。Skill 同时保存使用说明、结构化清理规则、参考资料，以及按需添加的界面和 C# 识别逻辑。应用为 .NET 10 / WPF，发布后不能假定用户安装 Python、Node.js 或 .NET SDK。

推荐在现有 AI 助手内加入 Skill Creator，复用现有清理候选与确认流程，增加聊天任务卡片和可重开的任务面板。Skill 是扩展包，Skill Creator 是编写和修订扩展包的内置能力，动态 UI 是应用提供的运行能力。仅添加一份创作提示词无法实现文件导入、联网取证、动态渲染和源码编译。

- src/SpaceMonger.Core/Services/Assistant/DiskAssistantService.cs：工具已接入当前助手，修改技能经 confirm_skill_change 确认；清理经 publish_recommendations、list_recommendations、select_recommendations、cleanup_recommendations。
- src/SpaceMonger.App/MainWindow.Copilot.cs：清理复用共享执行入口，并基于当前清单版本确认；可延续此入口。

- skills/unity-project-cleanup/SKILL.md：已有证据、识别条件、保留目录和风险说明，可作为创作示例，不能直接当作通用清理契约。

## 方案比较

1. 仅扩展 Markdown Skill：改动少，能覆盖宿主现有工具支持的流程；不能满足新识别逻辑及专用 UI。
2. 结构化规则 + 受约束 XAML + 可选 C# 源码：推荐。普通需求复用现有 UI，特殊需求携带自己的面板和识别逻辑。应用维护固定的发布、确认和执行边界。
3. 任意 WPF XAML + 任意源码插件：自由度大，但引入完整插件平台的维护成本；与当前需求相比不宜作为默认方案。可信高级扩展可以单独设计。

## Skill 包与运行约定

建议以 manifest.json 记录 ID、版本、描述、宿主协议版本、入口、需要的能力、引用材料摘要与完整包摘要。SKILL.md 保存 AI 工作方法和适用范围；rules.json 保存检测条件、候选路径解析、排除条件、再生方式、影响及风险；references/ 保存有用的资料片段与来源。ui.xaml 和 src/Detector.cs 均为可选项，没有需要就不生成。

结构化规则是确定性扫描和预览的输入。AI 不通过随意拼接删除路径执行操作。C# 扩展主要负责特殊发现、检测、分类和面板数据构建，输出候选与证据；实际删除统一由宿主处理。普通规则不要求编译源码。

用户 Skill 应存入当前用户可写的应用数据目录；内置 Skill 随包发布。保存时使用临时目录验证、原子提交和可回退版本，失败不替换有效版本。引用来源和包内容变动使之前的验证和信任记录失效。内置 Skill 不可被同名用户包静默遮盖。

## 创建流程

用户表达需求或选择创建清理技能 → 收集业务偏好与资料 → 提取有来源的规则草案 → 校验规则与所需宿主能力 → 在选定本机范围只读试扫 → 展示识别结果、保留项、恢复代价和不确定项 → 用户保存 Skill → 立即刷新技能目录，可继续执行或下次复用。

创建过程必须允许修改和放弃。保存 Skill 与执行一次清理是不同动作。对于某条未支持的规则明确解释缺少的能力，不能仅写入 Markdown 就宣称可执行。

资料导入首期明确支持文本、Markdown、公开网页和仓库中的可读取文本规则。PDF、DOCX 应通过 .NET 读取能力逐项支持，无法提取的扫描图片资料不能当作已读。资料带入的指令属于引用内容，不能授予运行命令或删除权限。网络请求须限制响应大小、跳转、超时和可访问目标，避免网页读取工具任意访问本机或内网服务。

规则库来源：用户指定的 https://github.com/Kiowx/c_cleaner_plus/ 。2026-10-25 已通过 GitHub API 与 raw 文本读取 main.py、config/rules_dev_tools.json、config/rules_cn_apps.json、config/common_custom_rules.json。main.py 中存在 npm、Yarn、pnpm 路径条目；另有 QQ 接收文件迁移条目，不能将迁移需求误导为删除整个 Tencent Files。config/common_custom_rules.json 包含 QQ 日志和微信日志；规则文件同时涉及 QQ 浏览器、QQ 音乐等不同产品，必须区分具体应用。

外部路径仅是识别线索。真实目录应结合用户路径、应用配置与只读本机证据确认；以用户机器的实际配置为准。未知、版本不匹配或无证据的条目保留为待核实。

## 何时使用哪种界面

- 路径、大小、风险、说明和勾选清理：复用现有清理建议列表。
- 少量参数、确认和保存：聊天内标准表单或任务卡片。
- 按 QQ 账号、Unity 项目、包管理器、缓存类型筛选；联动保留时间与大小预览；显示复杂明细：打开 Skill 任务面板。
- 自定义布局仍不足以表达识别逻辑时，才引入 C# 扩展；不能因为显示表格就生成源码。

AI 在聊天中确认的是业务选择，例如是否保留聊天图片、多久以前的数据、是否允许重新下载依赖；不要求用户选择 UI 技术。AI 依据宿主能力提出标准界面或专用面板，宿主验证和渲染。需要信息输入时可以在试扫前打开面板，不必等到最后一条回答。

## 聊天入口与完整交互

输入框现有 @ 菜单增加 Skill Creator 及用户技能；自然语言创建请求可路由到 Creator。创建或调用过程中，助手消息插入稳定的任务卡片，展示名称、进度、摘要以及打开面板、继续、查看结果等适用动作。卡片不是 Markdown 中的可执行链接，而是模型返回的结构化工具结果，由宿主渲染真实按钮。

小表单嵌入卡片；复杂面板以同主题的可调整大小任务窗口打开，默认由用户点击入口，避免反复抢焦点。窗口与聊天任务关联，关闭窗口仅隐藏 UI，取消任务使用明确的取消动作。重开恢复筛选和扫描状态。若未来主窗口空间允许，可以使用同一容器适配侧边任务区，不引入另一套协议。

示例：

用户：参考这份资料，帮我做 QQ 清理技能，聊天图片保留，只考虑日志和临时缓存。

助手：已整理规则，需要确认账号和目录。卡片显示「QQ 清理 · 待选择范围」，按钮为「打开清理面板」「查看规则来源」。

面板：展示已识别账号、缓存类别、保留设置和只读预览，未识别目录允许用户指定。点击「生成清理清单」将候选提交给宿主。

宿主：显示当前具体路径、大小、影响、删除方式与最终确认。执行结果回写卡片；用户可选择保存技能，下次通过 @QQ 清理或自然语言复用。

示例中的扫描结果和大小必须由真实扫描生成，不能使用模型估算替代。

## XAML 与 C# 的边界

借鉴 Loom-X 的两项独立机制：LoomX.PluginHost/SourcePluginCompiler.cs 使用 Roslyn 编译源码并缓存；LoomX/Controls/PluginUiPresenter.cs 把经过校验的声明式 UI 转为宿主主题控件。该 Presenter 使用 Avalonia，当前项目为 WPF，应复用契约和流程，不能直接复制控件。

推荐允许 Skill 使用受约束的 XAML 描述布局；明确这是宿主支持的子集，不承诺完整 WPF XAML/code-behind。通过受限 XML 解析为已知 UI 节点再创建 WPF 控件，不直接加载任意 XamlReader 内容。容器、文本、选项、列表、表格和命令绑定优先；不接受任意 CLR 类型、ObjectDataProvider、事件处理代码或自定义标记扩展。绑定仅访问宿主提供的数据，不访问任意对象。资源与主题由宿主提供。

按钮提交结构化命令和表单状态；筛选与预览等普通交互直接走确定性逻辑，不需要每次点击都调用模型。删除动作只能提交经宿主验证的候选 ID 与当前版本，过期面板先刷新，不能重用历史确认。

Roslyn 编译器、固定引用程序集、执行宿主随自包含发布包提供，不依赖终端 Python、dotnet build、用户 SDK 或临时 NuGet 还原。只允许固定宿主契约，校验与编译错误展示给 Creator 修正。C# 内容或能力变化后重新验证。

Loom-X 的 SourcePluginCompiler 已明确注明不提供进程安全沙箱。AssemblyLoadContext、命名空间白名单以及单独进程本身都不能阻止任意源码访问文件。因此源码模式必须先明确可信扩展的执行授权；独立执行进程可用于超时、取消和崩溃回收，但如要支持不可信源码，还必须实施并验证操作系统级隔离与最小权限，不能只声称删除通过宿主就已安全。普通规则与受约束 UI 不需要升级到任意源码模式。

## 分阶段交付与验收方向

第一阶段：Creator、资料导入、可验证规则、只读试扫、保存与更新、标准任务卡片，打通 npm 类场景。发布包在没有 Python 和 .NET SDK 的机器上可运行。

第二阶段：受约束 XAML 与任务面板、卡片打开和恢复、账号及缓存类型筛选，打通 QQ 示例；识别不确定项默认不进入清理。

第三阶段：带编译诊断、缓存、取消与明确授权的 C# 扩展运行链路；复核源码信任模型。无法建立隔离时只提供可信扩展模式，不宣称支持安全运行不可信源码。

每阶段验证真实用户流程、错误与取消路径；清理前验证扫描/清单版本、允许范围、保护路径、重解析点及最终目标。保存失败保留旧技能，取消确认不执行删除，来源或生成界面中的提示不得绕过宿主检查。所有改进通过应用窗口验收，最终按项目约定重新打包至 outputs 的可读时间目录。
